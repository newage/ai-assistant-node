# Журнал рішень: реакції на відповіді та лог питань без відповіді

## Проблема
Власник сайту не бачить, чи відповіді бота корисні, і не знає, на які питання бот не відповів (збій або відсутність даних у базі). Без цього FAQ у Pinecone поповнюється наосліп.

## Дано
- `POST /chat` → `{reply}`; збої Pinecone/Claude → 502 з текстом `failure`, невідома помилка → 500 — перевірено: `frontend/src/index.js` (`upstreamFailure`, error-handler)
- Ситуація «немає даних» → 200 з текстом `noData`, Claude не викликається — `frontend/src/index.js`
- Фронт знає `question` і `reply` на момент відображення — `frontend/public/index.html` (`send`, `addMessage`)
- Бази даних і залежності Neon немає; конфіг іде через `config.js` + `.env.example` — `frontend/package.json`, `frontend/src/config.js`
- Тести: Jest без мережі, залежності підміняються через `createApp(deps)` — `frontend/test/chat.test.js`
- Рейт-ліміт `/chat` — правило Vercel Firewall з id `chat` — `frontend/README.md`
- Контракт від користувача — `.agents/propose/answer.md`

## Концепт рішення
**Обрано:** клієнт після кліку на 👍/👎 шле `POST /answer` `{question, answer, reaction: good|bad}`; бекенд пише рядок у таблицю `reactions` (Neon, `@neondatabase/serverless`). Той самий механізм логування бекенд викликає сам у `/chat` для питань без відповіді.
**Чий:** запропонував розробник (`.agents/propose/answer.md`)
**Чому:** одна таблиця й один writer закривають обидві потреби, мінімум нових частин.
**Відкинуто:** альтернативи не розглядалися, розробник дав повний контракт (відхилення від норми воронки, прийнято свідомо).

## Вектор
```
Браузер ── POST /chat ──▶ pipeline ──▶ 200 reply
   │                         │ 502/500 (failure) ──▶ INSERT reactions(question, NULL, NULL)   ─┐ до відправки відповіді
   │                         │ 200 noData        ──▶ INSERT reactions(question, noDataText, NULL) ─┘
   └─ клік 👍/👎 ── POST /answer {question, answer, reaction} ──▶ INSERT ──▶ 201 ──▶ кнопку підсвітити, обидві заблокувати
                                                         не 201 ──▶ UI без змін
```
- Реакція необов'язкова; кнопки під кожним повідомленням бота-відповіддю, включно з `noData`; не показуються під вітанням і текстом помилки (відповіді немає).
- Усі значення в SQL йдуть лише параметрами (tagged template Neon), конкатенації немає; плюс валідація на вході.
- Помилка запису в БД на `/chat` не ламає відповідь користувачу (лише лог).

## Деталі
### Що логувати як «без відповіді»
**Рішення:** збої (502/500) → `answer=NULL`, `reaction=NULL`; `noData` → `answer` = текст `noData`, `reaction=NULL`. Рядок без реакції = питання без відповіді; збій відрізняється від noData тим, що `answer IS NULL`.
**Чому:** `reaction` лише good|bad (рішення розробника), тому значення error/no_data туди не йдуть; дірки в FAQ і збої розрізняються за `answer`.
**Змінено:** раніше було `reaction='error'|'no_data'` — відкликано за вказівкою розробника.
**Альтернатива:** лише збої або лише noData — втрачається один із двох сигналів.

### Повторний клік на реакцію
**Рішення:** після 201 обидві кнопки блокуються, один рядок на відповідь.
**Чому:** контракт не повертає id, тож змінити рядок неможливо; дублі в таблиці небажані.
**Альтернатива:** дозвіл змінювати (дубль рядків) або тоггл з upsert (потрібен id у відповіді).

### Неблокуючий клієнт
**Рішення:** запит `/answer` асинхронний і не блокує чат: поле вводу, відправка нових питань і інші кнопки працюють під час очікування. Блокується лише пара кнопок цього повідомлення (захист від подвійного кліку). Підсвітка тільки після 201; на помилку, не-201 або таймаут (`AbortController`, ~10 с) UI не змінюється, кнопки знову активні.
**Чому:** вимога розробника; реакція — другорядна дія, не повинна заважати діалогу.

### Міграція і підключення Neon
**Рішення:** скрипт міграції `frontend/scripts/migrate.js` (єдиний спосіб запуску — автоматичний, окремої npm-команди для ручного запуску немає) виконує `frontend/scripts/schema.sql` з `CREATE TABLE IF NOT EXISTS reactions` — повторний запуск безпечний. Підключення: `@neondatabase/serverless` (`npm install`), рядок з'єднання у `DATABASE_URL` (`config.js` + `.env.example`; на Vercel — у змінних проєкту, зазвичай її додає інтеграція Neon). Підключення створюється в окремому модулі `src/db.js` (за патерном `retrieval.js`), без з'єднання при імпорті; на Vercel запускається автоматично при деплої через скрипт `vercel-build` у `package.json` (`node scripts/migrate.js`, змінні беруться з середовища білда). Локальна БД: таблицю створює той самий скрипт, якщо розробник запустить його сам (`node --env-file=.env scripts/migrate.js`); окремого npm-скрипта для цього не робимо. Інструкцію додати в `frontend/README.md`.
**Чому:** вимога розробника; не треба пам'ятати про ручний крок. Збій міграції зупиняє деплой, стара версія лишається живою.
**Умови:** `DATABASE_URL` ввімкнена для Build; міграція ідемпотентна (виконується на кожному деплої); preview-деплої не повинні чіпати production-БД — окрема гілка Neon для Preview або змінна лише для Production (налаштування на боці Vercel/Neon). Правило «build step немає» в `CLAUDE.md` і `frontend/README.md` оновити.
**Альтернатива:** ручний запуск один раз на середовище — відхилено розробником.
**Тест:** логіку читання SQL покрити Jest без мережі; `--dry-run` не робимо.

## Відкриті питання
- Захист від спаму: правило Firewall для `/answer` налаштовується на боці Vercel (поза кодом). У коді — лише валідація.

## Припущення
- Таблиця: `id` bigserial PK, `question` text NOT NULL, `answer` text NULL, `reaction` varchar(20) NULL з CHECK (`reaction IN ('good','bad','error')`), `dt_created` timestamptz NOT NULL DEFAULT now(). Рядок з `reaction IS NOT NULL` = реакція користувача. DDL — `frontend/scripts/schema.sql` + npm-скрипт; `DATABASE_URL` в `.env.example`. Не блокує.
- Валідація `/answer`: тіло — JSON-об'єкт; `question`, `answer` — непорожні рядки, `question` ≤ `MAX_MESSAGE_CHARS`, `answer` ≤ ліміт довжини (нова змінна env, дефолт напр. 4000); `reaction` ∈ {good, bad}; невалідне → 400. Для `/answer` `answer` обов'язковий (NULL лише в серверних рядках без відповіді).
- Якщо `DATABASE_URL` порожній: запис пропускається, `/answer` повертає 503; `/chat` працює як раніше. Не блокує.
- Запис у БД у `/chat` робиться `await` до відповіді (функція Vercel «заморожується» після відповіді), його помилка ловиться й логується.
- Тести (Jest, без мережі, фейк writer через `createApp(deps)`): валідація `/answer` (400-кейси), 201 на валідне, 503 без БД, запис рядків на збої/noData у `/chat`, збій запису не ламає `/chat`, параметризований виклик writer; тест фронта не потрібен (немає інфраструктури).
