# Design

## Context

`scripts/seed-pinecone.js` будує записи (`toRecords`), перевіряє унікальність id і шле все через `upsertRecords` пачками по 96. Індекс створений з integrated embedding: Pinecone сам рахує вектор із поля `text`. Мотивація та межі описані в `proposal.md`, вимоги в `specs/faq-seeding/spec.md`.

Перевірено в установленому `@pinecone-database/pinecone@9.0.0`:
- `index.fetch({ ids })` повертає `records` за id з `metadata?` і ліміт ids на запит виставляє API (у плані пачки по 100). Метод не має окремого режиму для integrated-індексів.
- Документація SDK не гарантує, що поле, з якого рахується ембедінг (`text`), повертається у `fetch`. Покладатись на порівняння `text` напряму не можна без перевірки на реальному індексі.

## Goals / Non-Goals

**Goals:**
- Відправляти лише нові й змінені записи, джерело істини для порівняння: сам індекс.
- Логіка порівняння покрита тестами без мережі.
- Деградація до «відправити все», а не до пропуску змін.

**Non-Goals:**
- Видалення «осиротілих» записів.
- Локальний манифест чи кеш між запусками.
- Зміна схеми id чи формату `faq.sample.json`.

## Decisions

**1. Порівнювати одне поле `content_hash`, а не п'ять полів.**
До кожного запису додається metadata-поле `content_hash` (sha256, hex) від нормалізованого JSON `[embeddedText, answer, lang, type, project ?? null]`. Metadata гарантовано повертається `fetch`, тоді як повернення `text` не гарантоване. Запис без `content_hash` (старі записи) автоматично вважається зміненим.
- Альтернатива: порівнювати поля напряму. Простіше, але якщо `text` не повертається, кожен запис завжди «змінений» і фіча не працює. Хеш цього уникає.
- Альтернатива: локальний манифест `id → hash`. Розходиться з індексом після перестворення або сіду з іншої машини.

**2. Модуль `scripts/seed-lib.js`.**
Виносяться `toRecords`, `contentHash`, `diffRecords(records, existing)` (чиста функція → `{ toSend, newCount, changedCount, unchangedCount }`) і `fetchExisting(index, ids)` (пачки по 100, приймає будь-який об'єкт із методом `fetch`). `seed-pinecone.js` лишається entry-точкою: аргументи, env, цикл відправлення. Модуль лежить у `scripts/`, а не в `src/`, бо це не код сервера.
- Альтернатива: тестувати через запуск скрипта. Скрипт виконується при імпорті, тому потрібен розподіл.

**3. Dry-run залежить від наявності ключів.**
Якщо `PINECONE_API_KEY` та `PINECONE_INDEX_NAME` задані, `--dry-run` читає індекс і друкує повний підсумок (читання нічого не змінює). Якщо ні, друкує лише кількість записів, як зараз. Нового прапорця не вводимо.

**4. Помилка читання індексу зупиняє сід.**
Якщо `fetch` падає, скрипт завершується з помилкою і не переходить мовчки до повного upsert: так не буде несподіваних витрат на ембедінги.

**5. Порядок і розмір пачок.**
`fetch` по 100 id (за потреби зменшити, якщо API відхилить розмір), `upsertRecords` як і раніше по 96. Відправляється відфільтрований список, нумерація прогресу рахується від його довжини.

## Risks / Trade-offs

- [Перший запуск після зміни відправить усі 310 записів, бо `content_hash` ще немає] → очікувано, одноразово, описано в README та proposal.
- [Вставка питання посередині `questions` зсуває номери наступних чанків і ці чанки відправляться як змінені] → правило «додавати в кінець» у README. Коректність не страждає, лише зайві ембедінги.
- [Хеш не бачить змін, зроблених в індексі руками] → прийнятно: індекс наповнюється лише цим скриптом. Для примусового перезапису є простий шлях: видалити запис в індексі, і він стане «new».
- [Зміна формули хеша змусить відправити все] → формула фіксується тестом, змінювати її треба свідомо.
- [`fetch` повертає не те, що очікуємо, на реальному індексі] → задача 1.1 перевіряє це вручну до решти роботи. Fallback (немає `content_hash` → відправити) не дає втратити зміни.
  - Перевірено 2026-10-19 на реальному індексі: `fetch` повертає `metadata` з `answer`, `lang`, `parent_id`, `text`, `type` (`content_hash` ще немає). `text` повертається, але рішення порівнювати хеш лишається в силі (повернення `text` не гарантоване контрактом). Відсутній id не потрапляє в `records`.

## Migration Plan

1. Задеплоїти зміну скрипта (деплоїти нічого не треба, скрипт запускається локально).
2. Один раз виконати `npm run seed`: усі записи отримають `content_hash`.
3. Далі `npm run seed` відправляє лише дельти. Відкат: повернути попередню версію скрипта, додаткове поле `content_hash` нікому не шкодить.
